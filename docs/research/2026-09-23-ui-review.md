# Dietitian panel — independent UI review

23 September 2026 · Review mode · No code changes

## Assessment and scope

The panel looks credible and calm. The cool ground, restrained emerald, strong text contrast and Fraunces headings give it a recognisable identity. The client table is the strongest everyday screen: compact rows, clear columns, useful search and filters. The main weakness is moving from a five-client demonstration to a working day with 40 clients. Some routes require unnecessary backtracking, while editors and reports consume considerable space without keeping the decision-relevant information in view.

Read AGENTS.md and all six required references before reviewing. Generated and visually inspected **all 11 PNGs** in `apps/dietitian_panel/test/goldens/`; read `main.dart`, all of `lib/panel/`, the shared theme, and the relevant demo screens and state. Auth screens and the video placeholder were also read. Real-panel observations are **code-based**, not claims about screenshots or a live account.

The screenshot command passed **11/11 captures**. Flutter was absent from the shell PATH, so the installed `$HOME/development/flutter/bin/flutter` was used with the requested flags and `FLUTTER_ROOT`; SDK-cache access required sandbox escalation. These are capture tests, not visual regression assertions. Captures use a 1600-logical-pixel desktop width, 1.5× scale and differing heights; the tall editor captures are not evidence that a normal laptop shows the entire form. Interaction findings below were traced in code, not independently reproduced in a browser.

Accepted as deliberate: no money features (P6), two competing plan editors (P4), labelled invented interview questions/thresholds/exchange values, separate offline demo and real app (#78), desktop-only panel (#38), and the placeholder logo. Missing marketplace, real plans, video infrastructure, structured health fields, invite-email delivery and password reset are already documented/deferred. The known green and ochre semantic tensions are not findings. No palette change or locked product-decision change is proposed.

## Ranked findings

Priority means impact on this UI review: **High** interrupts or misdirects a core task; **Medium** causes avoidable errors or repeated work; **Low** concerns consistency and discoverability. Demo defects are not claims that real messages or health data have been affected.

### 1. High · bug/inconsistency — A message draft follows the user into another conversation

**Evidence:** `09-mesajlar.png`; [messages_screen.dart:64](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/messages_screen.dart:64), [controller and send action:281](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/messages_screen.dart:281).

The unkeyed conversation widget retains its controller when `clientId` changes. Type advice for Elif, select Merve, then press send: the retained text is added to Merve's conversation. **Fix:** keep drafts per client and restore the appropriate draft on selection; bind the send action to that draft's recipient. A simple client key prevents carryover but would also discard drafts unless they are stored separately.

### 2. High · bug/inconsistency — The conversation list cannot accommodate 40 clients

**Evidence:** `09-mesajlar.png`; [messages_screen.dart:41](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/messages_screen.dart:41).

The left card contains every client in a plain `Column`, inside a height-constrained screen. Only the message thread scrolls. With 40 rows, the list overflows and later conversations cannot be reached by scrolling. **Fix:** give the conversation list its own bounded `ListView`; keep the selected client visible. This is a defect in the existing list, not a request to implement real chat ahead of the roadmap.

### 3. High · bug/inconsistency — The exchange editor loses its most important numbers

**Evidence:** `06-degisim-listesi.png`; [exchange_plan_editor_screen.dart:89](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/exchange_plan_editor_screen.dart:89), [app_typography.dart:42](/home/can/projects/dietician-app/packages/core/lib/src/theme/tokens/app_typography.dart:42).

“PLANDA” and “HEDEF” render as black blocks in the generated PNG. Both use `headlineSmall`, which the shared text theme does not define. The capture exposes a fallback font; a browser may render fallback text rather than blocks, but it still misses the intended typography. **Fix:** use an existing defined slot or explicitly define this slot with the approved face and tabular figures. Verify the next capture and browser rendering.

### 4. Medium · bug/inconsistency — The freeform summary looks like calculated meal totals

**Evidence:** `05-plan-editoru.png`; [plan_editor_screen.dart:93](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/plan_editor_screen.dart:93), [demo_repository.dart:176](/home/can/projects/dietician-app/apps/dietitian_panel/lib/demo/demo_repository.dart:176).

“Kalori / Protein / Karbonhidrat / Yağ” appear immediately above editable meals. Changing food amounts leaves these values unchanged; calories are the manually set target, and macros are separate demo values. CONTEXT.md already acknowledges this limitation. **Fix:** label the block “Örnek makro hedefleri — öğünlerden hesaplanmaz” and the calorie value “Belirlenen enerji hedefi.” This is a presentation correction, not a demand to settle P4 or add food calculations.

### 5. Medium · bug/inconsistency — Leaving anamnez silently discards entered work

**Evidence:** `07-yeni-danisan-anamnez.png`; [intake_form_screen.dart:82](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/intake_form_screen.dart:82), [cancel action:214](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/intake_form_screen.dart:214).

After entering several health/history fields, “Vazgeç” immediately pops the page; the app-bar back action is also unguarded. Nothing saves the form before `_save`. This conflicts with the design rule requiring confirmation for destructive cancellation. **Fix:** detect a dirty form and ask “Değişiklikler kaydedilmedi. Çıkmak istiyor musunuz?” with “Düzenlemeye devam edin” and “Değişiklikleri silin.” Apply it to both exit paths.

### 6. Medium · bug/inconsistency — Declined invitations still say they are waiting

**Evidence:** Real panel, [real_overview_screen.dart:265](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel/real_overview_screen.dart:265) and [status mapping:329](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel/real_overview_screen.dart:329).

A declined relationship is non-openable and has no projected active-client name, so its first cell says “Davet bekliyor” while its status says “Reddedildi.” A dietitian scanning unanswered invites receives contradictory instructions. **Fix:** derive the first-cell fallback from the relationship status; use “Davet reddedildi” for declined records and reserve “Davet bekliyor” for pending ones.

### 7. Medium · bug/inconsistency — Real-panel failures provide no usable recovery

**Evidence:** [real_overview_screen.dart:64](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel/real_overview_screen.dart:64), [error state:351](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel/real_overview_screen.dart:351), [real_client_detail_screen.dart:33](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel/real_client_detail_screen.dart:33).

List/detail failures expose raw exception text without retry; a separate name-fetch failure silently becomes dashes. After a transient connection problem, a dietitian cannot tell whether names are absent or failed to load. **Fix:** preserve available rows, show a short Turkish explanation and “Tekrar deneyin,” and retry the relevant provider. The explicit deferral of English **auth** errors (#44) does not cover these client-data screens.

### 8. Medium · design — Triage opens the record instead of the task

**Evidence:** `01-genel-bakis.png`, `03-danisan-karti.png`; [overview_screen.dart:185](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/overview_screen.dart:185), [client_detail_screen.dart:29](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/client_detail_screen.dart:29).

“47 saattir mesajı yanıtsız” leads to the generic client detail. That page covers the rail and has no conversation link; answering requires going back, selecting Mesajlar and finding the client again. Chat and appointments already exist in the demo. **Fix:** use task-specific links—“Mesajı yanıtlayın,” “Randevuyu açın,” “Ölçümleri inceleyin”—that open the corresponding existing context. Keep a secondary client-record link.

### 9. Medium · missing feature — The real client list has no quick lookup

**Evidence:** [real_overview_screen.dart:26](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel/real_overview_screen.dart:26); compare `02-danisanlar.png` and [clients_screen.dart:38](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/clients_screen.dart:38).

The demo already has name search and filters. The real panel renders all relationships with no search, so finding a specific person among 40 active clients plus invites requires scanning or scrolling. PLANNING's real-panel deferrals do not include basic list lookup. **Fix:** add local name/email search and a small active/pending/declined filter above the existing table. This needs no new health fields or rail destination.

### 10. Medium · design — Editor width and scrolling separate the decision from the work

**Evidence:** `05-plan-editoru.png`, `06-degisim-listesi.png`; [plan_editor_screen.dart:39](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/plan_editor_screen.dart:39), [exchange editor meal rows:258](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/exchange_plan_editor_screen.dart:258).

Both screens spend nearly the full desktop width on short food/group labels and place the approval action and energy context at the top of one long scroll. After editing dinner, the dietitian must return to the top to compare totals and approve; exchange controls sit far from their group labels. **Fix:** constrain the working column and keep a compact energy/status/action summary visible beside it or in a sticky bar. Keep both editors and their different models.

### 11. Medium · bug/inconsistency — Weight charts depict equal intervals even when dates differ

**Evidence:** `03-danisan-karti.png`, `10-takip.png`; [weight_chart.dart:100](/home/can/projects/dietician-app/apps/dietitian_panel/lib/widgets/weight_chart.dart:100).

Point positions use the observation index, while the axis labels imply calendar time. A weigh-in after one day and another after three weeks receive equal horizontal spacing, hiding the gap and changing the apparent rate. The regularly spaced seed data does not reveal this defect. **Fix:** position points by elapsed date within the displayed range and include readable endpoint dates; retain the existing target line and direct value label.

### 12. Medium · design — Takip is a gallery, not a scan of 40 clients

**Evidence:** `10-takip.png`; [reports_screen.dart:31](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/reports_screen.dart:31), [weight_chart.dart:21](/home/can/projects/dietician-app/apps/dietitian_panel/lib/widgets/weight_chart.dart:21).

Each client gets a 170-pixel chart plus card chrome. Burak's “hedefe doğru” result also lacks the last measurement date, although the overview correctly flags his 21-day measurement gap. Scanning 40 people requires many screens and makes old progress look current. **Fix:** start with compact rows showing name, latest weight/date, change and existing target-based verdict; expand a row for its full chart. Reuse the existing freshness signal without inventing new thresholds.

### 13. Low · bug/inconsistency — Secondary controls do not follow the same compact tokens

**Evidence:** `02-danisanlar.png`, `03-danisan-karti.png`, `08-randevular.png`; [app_theme.dart:58](/home/can/projects/dietician-app/packages/core/lib/src/theme/app_theme.dart:58).

The filled plan action has the specified modest corner radius, while the adjacent outlined action is a pill. Search, dropdowns and chips also have visibly different heights. The theme styles filled buttons but has no outlined-button theme; the input token is only a minimum, with shared padding. **Fix:** theme outlined/text buttons and relevant form controls using the compact density, aligning their visible heights and corner treatment. Preserve adequate click targets. This enforces the existing rules rather than challenging the palette.

### 14. Low · bug/inconsistency — Turkish tone and formatting change between surfaces

**Evidence:** `03-danisan-karti.png`, `07-yeni-danisan-anamnez.png`, `09-mesajlar.png`; [detail labels:546](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/client_detail_screen.dart:546), [intake actions:211](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/intake_form_screen.dart:211), [real invite actions:174](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel/real_overview_screen.dart:174), [real empty state:400](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel/real_overview_screen.dart:400).

The real dialog says “Vazgeçin,” while the demo says “Vazgeç,” “dene” and “oluştur.” Uppercasing produces “BESLENME TIPI” instead of “BESLENME TİPİ”; values use “72.4” rather than Turkish “72,4.” “Marketplace” introduces unnecessary English in the real empty state. **Fix:** apply the chosen siz register consistently, use Turkish-aware case/number formatting, and say “Diyetisyen bul özelliği açıldığında…” in the empty state. Keep familiar professional terms such as anamnez and BMH; “yapay zekâ taslağı” is clearer than alternating with “AI taslağı.”

### 15. Low · design — Hatırlatmalar sounds like an inbox but opens settings

**Evidence:** `11-hatirlatmalar.png`; [settings_screen.dart:21](/home/can/projects/dietician-app/apps/dietitian_panel/lib/screens/settings_screen.dart:21), [panel_shell.dart:68](/home/can/projects/dietician-app/apps/dietitian_panel/lib/panel_shell.dart:68).

The bell destination sits alongside daily working screens, but contains timing switches and channel preferences. A dietitian looking for reminders awaiting action finds configuration instead. **Fix:** call it “Hatırlatma ayarları” and place it in a visually separate utility area, or expose these settings from Randevular while retaining a clear demo entry point. No additional notification inbox is implied.

## Launch navigation assessment

**Now:** retain the real panel's two destinations, **Genel Bakış → Profil**, as required by #53. Improve lookup within the existing overview; do not add empty demo destinations to the real rail. The absence of a real marketplace or plan editor is already accounted for in PLANNING and QUESTIONS C1/C3.

**Opinion for when the corresponding workflows work:** use **Genel Bakış → Danışanlar → Mesajlar → Randevular → Takip**, with profile/settings separated below. Messages slightly ahead of appointments suits repeated short responses across 40 clients; interview evidence could justify keeping their current order. Overview and clients should remain first. “Takip” is broad but serviceable; use “Ölçüm takibi” if the eventual scope remains measurements. Keep reminder configuration out of the primary daily-work group. Add marketplace-request handling only when Can resolves that flow; do not invent a launch destination now.

## Brainstorm

**Opinion only — larger ideas to explore, not additional defects, agreed scope or product decisions.**

- **A compact daily work queue:** group existing signals by client, so Zeynep's unanswered message and missed appointment can be handled together. Keep reasons explicit and thresholds labelled as assumptions during interviews.
- **A persistent client workspace:** retain the rail and a narrow identity/context strip while opening the plan, conversation or measurements. This could reduce repeated navigation without combining the demo and real entry points.
- **An editor comparison with the same surrounding layout:** place both P4 prototypes inside identical client-context and approval chrome, then compare editing effort. Dietitians could judge the model without differences in page width and summary placement biasing the choice.
- **A 40-client usability session:** ask a dietitian to find one named client, answer an overdue message, inspect a stale measurement and review dinner before approving. Use task completion and observed hesitation to choose density; do not make the interface uniformly smaller.
- **An explicit interview layer:** keep “örnek” and “tahminimiz” beside the relevant content, but consider an expandable area for the longer interview questions. The working hierarchy would remain visible while preserving the demo's honesty and research purpose.

No rule challenge is necessary for these recommendations. The existing palette and typography direction are worth keeping; the next improvements are mainly consistent implementation, context and task flow.
